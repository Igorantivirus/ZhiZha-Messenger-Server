# TLS и ссылка-приглашение

Весь трафик сервера — HTTPS и WSS. Crow обслуживает HTTP и WS-upgrade на
одном порту, поэтому один TLS-контекст покрывает оба транспорта.
Незашифрованного режима нет.

## Конфигурация

Секция `tls` в `config.json` (целиком опциональна — при отсутствии
действуют дефолты):

```jsonc
"tls": {
    "certFile": "",        // путь к своему сертификату (PEM); пусто = автогенерация
    "keyFile": "",         // путь к приватному ключу (PEM)
    "scheme": "zhizha",    // имя URI-схемы в ссылке-приглашении
    "address": ""          // домен/IP для ссылки; пусто = локальный IP автоматически
}
```

Правила:
- **Оба пути заданы** — используется пользовательская пара. Невалидная
  (ключ не от этого сертификата, срок истёк/не наступил, файл не читается)
  → сервер **не стартует** (fail-fast: молча подменять указанный
  пользователем сертификат самоподписанным опасно).
- **Оба пути пусты** — сервер использует ранее сгенерированную
  самоподписанную пару из рабочей директории, а если её нет (или она
  испорчена/просрочена) — генерирует новую: EC P-256, SHA-256, срок ~10 лет.
- **Задан только один путь** — ошибка конфигурации, сервер не стартует.

## Файлы в рабочей директории

Рабочая директория — та, где лежит файл БД (`databaseFile`). Сервер
создаёт там:

| Файл | Что это |
|---|---|
| `tls-cert.pem` | автосгенерированный сертификат (переиспользуется между запусками) |
| `tls-key.pem` | приватный ключ к нему |
| `tls-cert.sha256` | fingerprint сертификата прошлого запуска |

Переиспользование пары критично: fingerprint должен быть стабилен между
рестартами, иначе все розданные ссылки-приглашения протухают.

## Ссылка-приглашение

При старте сервер печатает ссылку:

```
{scheme}://{address}:{port}/#{fingerprint}
```

Пример: `zhizha://192.168.1.10:8080/#3f5a...c9e1`

- `scheme` — из конфига (`zhizha` по умолчанию). Должна соответствовать
  грамматике URI-схемы: `[a-z][a-z0-9+.-]*`.
- `address` — из конфига (домен/внешний IP), иначе локальный IP машины,
  определённый автоматически (кроссплатформенно через Asio: UDP-connect
  без отправки пакетов + getsockname).
- `fingerprint` — SHA-256 от DER-представления сертификата, 64 hex-символа
  в нижнем регистре.

### Правило для клиента (pinning)

1. Распарсить ссылку: host, port, fingerprint (из fragment).
2. Установить TLS-соединение с host:port, **отключив стандартную CA-проверку**.
3. Взять сертификат сервера из handshake, посчитать SHA-256 от DER.
4. Совпало с fingerprint из ссылки → доверять и работать (HTTPS + WSS).
   Не совпало → **разорвать соединение**, это MITM или другой сервер.

Fragment (`#...`) по сети не передаётся — он живёт только на стороне
клиента, поэтому fingerprint не «светится» в запросах.

## Смена сертификата

При каждом старте сервер сравнивает fingerprint текущего сертификата с
сохранённым в `tls-cert.sha256`. Если отличается — перед ссылкой печатается
плашка:

```
!!!  ССЫЛКА ИЗМЕНИЛАСЬ! Сертификат сервера сменился.  !!!
```

Это значит, что все ранее розданные ссылки не пройдут pinning и клиентам
нужно дать новую ссылку. Штатные причины смены: подложили/убрали
пользовательский сертификат, удалили `tls-*.pem`, истёк срок.

## Ограничения (осознанные)

- Pinning по fingerprint работает для **нативных клиентов**. Браузерный
  web-клиент так не сможет (браузер не даёт управлять проверкой
  сертификата) — ему нужен нормальный CA-сертификат (Let's Encrypt) в
  `certFile`/`keyFile`.
- Автоопределение адреса даёт **локальный** IP. Для доступа из интернета
  указывайте `address` (домен или внешний IP) вручную.
- Ротация сертификата без потери старых ссылок не поддерживается
  (нет механизма cross-signing) — смена сертификата = новая ссылка.
