## Отложено (сделать позже)

### 1. Утечка `userdata` при отклонённом upgrade
**Где:** [WsServer::onAccept](../src/Transport/WsServer.hpp), [onClose](../src/Transport/WsServer.hpp)
`new protocol::UserId` выделяется в `onAccept` и освобождается в `onClose`.
Нужно убедиться, что Crow гарантированно вызывает `onClose` для каждого
успешного `onOpen`. Если соединение прошло `onAccept` (userdata выделен),
но `onOpen`/`onClose` не случились — память утечёт.
**Что сделать:** проверить контракт Crow; при необходимости освобождать
userdata в самом `onAccept`, если возвращаем `true`, но соединение потом
не открылось. Либо хранить userId не в сыром `new`, а владеюще.

### 2. Нет server-side heartbeat / таймаута мёртвых соединений
**Где:** весь WS-слой + [SessionManager](../src/Sessions/SessionManager.hpp)
Сервер отвечает на `Ping` от клиента (`Pong`), но сам не пингует и не
закрывает «висящие» соединения (полузакрытый TCP). `SessionManager`
будет накапливать мёртвые сессии.
**Что сделать:** периодический серверный ping + закрытие по таймауту
(нет pong за N секунд → `conn.close()` и удаление сессии).

### 3. `sendToUser` шлёт в соединение без обработки ошибок
**Где:** [SessionManager::sendToUser](../src/Sessions/SessionManager.hpp)
Указатели на соединения копируются под локом, `send_text` вызывается уже
без лока. Если соединение умерло в этом окне, поведение зависит от Crow.
**Что сделать:** обернуть `send_text` (try/catch или проверка состояния),
не падать на одном мёртвом адресате при рассылке остальным.

### 4. Рассылка по WS синхронная — блокирует поток-обработчик
**Где:** [ChatService::onSendMessage](../src/ChatService/ChatService.hpp),
[SessionManager::sendToUser](../src/Sessions/SessionManager.hpp)
Цикл рассылки `NewMessage` вызывает `conn->send_text` синхронно для каждого
онлайн-участника. Один медленный/забитый сокет тормозит весь цикл и блокирует
поток, который сейчас обрабатывает сообщение отправителя. Ack отправителю уже
вынесен *до* рассылки (главный симптом снят), но сама рассылка остальным
по-прежнему держит поток.
**Что сделать:** вынести отправку из обработчика — сделать неблокирующей.
Crow построен на Boost.Asio, и до `io_context` приложения можно дотянуться
(`app.get_io_context()` / `io_service` у Crow), поэтому отправку можно
`post(...)`'ить в `io_context` и не блокировать поток-обработчик. Варианты:
- `boost::asio::post(app.get_io_context(), [conn, payload]{ conn->send_text(payload); })`
  на каждого адресата — рассылка уходит в реактор, обработчик сразу свободен;
- либо очередь исходящих на сессию + один writer, чтобы не было гонок
  параллельных `send_text` по одному соединению.
Учесть время жизни `conn` (может закрыться к моменту исполнения задачи —
см. #3) и потокобезопасность относительно `onClose`.

### 5. Доставка только онлайн-участникам, нет оффлайн-механики
**Где:** [ChatService::onSendMessage](../src/ChatService/ChatService.hpp)
`NewMessageEvent` рассылается, но получают только онлайн. Оффлайн-участник
узнает о сообщении лишь при следующем `getMessages`. Нет unread-счётчика,
нет пушей.
**Что сделать:** unread-счётчик на комнату (есть `lastReadMessageId` в схеме),
позже — push-уведомления для оффлайн-устройств.

### 6. Логирование через `std::cout`
**Где:** [WsServer::onAccept / onOpen](../src/Transport/WsServer.hpp)
`std::cout` без синхронизации — при многопоточном Crow строки логов
перемешиваются между потоками. Это отладочный вывод.
**Что сделать:** потокобезопасный структурированный логгер; убрать
отладочные `std::cout`.

### 7. Нет ограничения размера входящего WS-кадра на уровне приложения
**Где:** [WsServer::onMessage](../src/Transport/WsServer.hpp)
Текст сообщения проверяется на `maxMessageSize` уже в `onSendMessage`, но
сам JSON-кадр любого размера сначала целиком парсится (аллокация до
проверки). Большой кадр = лишняя нагрузка.
**Что сделать:** ограничить размер кадра на входе (Crow max payload или
ранняя проверка `data.size()` до парсинга).

### 8. WS-события комнат есть в протоколе, но HTTP-команд под них нет
**Где:** [Protocol/Ws.hpp](../src/Protocol/Ws.hpp), [ChatService](../src/ChatService/ChatService.hpp)
В протокол добавлены все события о комнатах (`RoomCreated`, `RoomDeleted`,
`RoomUpdated`, `UserJoined`, `UserLeft`). Сейчас реально рассылаются:
- `RoomCreated` — из `createRoom` (приглашённым);
- `UserJoined` — из `inviteUser`;
- `UserLeft` — из `leaveRoom` (оставшимся).

Не задействованы (событие в протоколе есть, источника пока нет):
- **`RoomDeleted`** — нет явной команды удаления комнаты. Комната удаляется
  только неявно внутри `leaveRoom` (ушёл последний / owner остался один),
  и там слать событие **некому** — участников не осталось. Понадобится,
  когда появится `DELETE /rooms/<id>` (удаление owner'ом комнаты, где ещё
  есть участники) → разослать `RoomDeleted` всем перед `roomRepo_.remove`.
- **`RoomUpdated`** — нет команды изменения комнаты. Нужен
  `PATCH /rooms/<id>` (сменить имя/политики) → после мутации разослать
  `RoomUpdated{room}` всем участникам.
**Что сделать:** добавить HTTP-команды `DELETE /rooms/<id>` и
`PATCH /rooms/<id>` + сервисные методы `deleteRoom` / `updateRoom`, которые
рассылают соответствующие события. Получателей `RoomDeleted` фиксировать
**до** `remove` (CASCADE сносит `roomMembers`).

## Уже сделано (для контекста)

- **Бродкаст не шлёт `NewMessage` самому отправителю.** Отправитель
  получает только `MessageAckEvent` (локальный id → глобальный messageId).
  → [ChatService::onSendMessage](../src/ChatService/ChatService.hpp).
- **Ack уходит до рассылки остальным.** Подтверждение отправителю больше не
  ждёт синхронного цикла рассылки `NewMessage` всем участникам — порядок
  в `onSendMessage`: `create → ack отправителю → рассылка остальным`.
  (Сама рассылка пока синхронна — см. отложенный #4.)
- **Единый источник времени создания.** `IMessageRepository::create`
  возвращает готовый `Message` с `createdAt` из БД; это же время идёт в ack
  и в `NewMessage`. Раньше брался второй замер `getCurrentTime()`, и время в
  ack расходилось с записанным в БД.
- **Создание/покидание комнаты убрано из WS** — только HTTP REST.
  Из протокола удалены `WsMessageType::CreateRoom/LeaveRoom` (команды).
- **События о комнатах рассылаются по WS после HTTP-мутаций.**
  `RoomCreated` (несёт полную `Room`) — приглашённым из `createRoom`;
  `UserJoined` — из `inviteUser`; `UserLeft` — из `leaveRoom`. В протокол
  добавлены также `RoomDeleted` и `RoomUpdated` — пока без источника (см. #8).
- **Ошибки чата доходят до клиента по WS.** Единая таблица маппинга
  `ChatError → код/текст` живёт в `HttpHelpers` (приватная `ChatErrorInfo`
  + `mapChatErrorInfo`); HTTP использует `mapChatError`, WS — `mapChatErrorWs`.
- **Парсинг входящих сообщений — только через протокольный `variant`.**
  `parseMessageFromClient` + `std::visit`; ручной разбор `json.value("type")`
  и `dispatch` удалены. → [WsServer::onMessage](../src/Transport/WsServer.hpp).
- **`userIdOf` проверяет `nullptr`.** Возвращает `std::optional`; при
  отсутствии userdata соединение закрывается / отдаётся `Unauthorized`
  вместо разыменования нулевого указателя (UB).
